# تحویل به بک‌اند: هماهنگی امضای دیجیتال با قرارداد فعلی

تاریخ: ۲۰۲۶/۱۱/۱۹

## مبنا و وضعیت این سند

این سند با کد بک‌اند روی `feat/refactor` در کامیت `f23cbb3` تطبیق داده شده است. رفتار محیط آزمایشی و اتصال واقعی به رخ هنوز نیاز به آزمون دارند.

فرانت‌اند دیالوگ امضا، رسم یا آپلود PNG، دریافت OTP، ثبت PIN و OTP، پیگیری نتیجه و دریافت PDF را پیاده کرده است. اتصال مستقیم به رخ، ایجاد رمز امضا، تنظیم محل امضا روی PDF و ایجاد دور جدید امضا در این نسخه انجام نمی‌شود.

## ۱. اتصال به ساختار فعلی قرارداد و گردش‌کار

ساختار فعلی فرانت‌اند:

- جزئیات معاملهٔ کاربر از `GET /v1/deals/u/{deal_id}` دریافت می‌شود.
- جزئیات در پروفایل کارگزار از `GET /v1/deals/{broker_id}/p/{deal_id}` دریافت می‌شود.
- پاسخ جزئیات شامل `current_workflow` و `next_available_actions` است.
- اکشن‌های معمول از مسیرهای `/workflow-actions` مرتبط ارسال می‌شوند. اکشن `sign` اکنون از این مسیر جدا شده و فقط دیالوگ و API اختصاصی امضا را باز می‌کند.
- مسیر اختصاصی امضا `/v1/deals/{deal_id}/contract-signature` است. بک‌اند تنها هویت شخصیِ خریدار یا فروشنده را می‌پذیرد؛ در پروفایل کارگزاری فرانت‌اند کنترل امضا را نمایش نمی‌دهد.

انتظار فرانت‌اند از پاسخ جزئیات:

```json
{
  "id": 42,
  "current_workflow": {
    "group": "نام پویای گروه",
    "step": "نام پویای مرحله",
    "header_description": "توضیحات مرحله"
  },
  "next_available_actions": [
    {
      "transition_id": 123,
      "action": "sign",
      "action_text": "امضای قرارداد",
      "destination_step": 456,
      "destination_step_name": "نام پویای مرحله بعد"
    }
  ]
}
```

اعداد و نام‌ها صرفاً نمونه‌اند. فرانت‌اند هیچ نام یا کد مرحله‌ای مانند `both_signature` را مبنای تصمیم نمی‌گیرد.

### الزامات گردش‌کار — مطابق مستند مبنا

- ارائهٔ اکشن `sign` مطابق نقش و وضعیت واقعی معامله؛ `can_sign` مرجع نهایی مجوز ارسال است.
- ثبت قطعی امضای طرف اول قبل از مجازشدن طرف دوم؛ PDF طرف دوم باید شامل امضای اول باشد.
- رد تلاش برای عبور از مرحله با ارسال مستقیم transition امضا به API عمومی گردش‌کار.
- پیشرفت مرحله فقط بر اساس نتیجهٔ قطعی امضای دیجیتال، با جلوگیری از گذار تکراری هنگام reconciliation هم‌زمان.
- در عبور خودکار معاملات کم‌مبلغ، جزئیات معامله و اکشن‌ها باید وضعیت جدید را منعکس کنند.
- رد امضا معامله را در مرحلهٔ امضا نگه می‌دارد و باعث انتقال وجه نمی‌شود.
- پرداخت یا استرداد در انتظار و عملیات امضای حل‌نشده باید `can_sign` را غیرفعال کنند.
- یک دور امضا برای هر معامله؛ ویرایش قرارداد پس از آغاز امضا نباید بی‌صدا سند مربوط به همان دور را جایگزین کند. ایجاد دور تازه نیازمند تصمیم و تغییر بک‌اند است.

### رفتار پیاده‌سازی‌شده و موارد باز

۱. **دسترسی طرف منتظر:** بک‌اند هنگام پردازش امضا اکشن‌های گردش‌کار را موقتاً حذف می‌کند، اما API اختصاصی همچنان وضعیت را به طرفین می‌دهد. اگر اکشن `sign` وجود نداشته باشد ولی PDF قرارداد در فهرست اسناد باشد، فرانت‌اند برای طرف معامله در پروفایل شخصی snapshot می‌گیرد و فقط با پاسخ موفق و `is_you` دکمهٔ «مشاهده وضعیت امضای قرارداد» را نمایش می‌دهد.

۲. **PDF امضاشده پس از گذار:** فهرست اسناد آخرین نسخه را برمی‌گرداند. فرانت‌اند نسخه‌ای با توضیح `Digitally signed deal contract PDF` را با عنوان «نسخهٔ امضاشدهٔ قرارداد» نمایش می‌دهد؛ این عنوان می‌تواند به نسخهٔ تک‌امضا نیز اشاره کند.

۳. **هویت امضاکننده:** بک‌اند دسترسی را با `request.user.actor` و نقش خریدار یا فروشنده بررسی می‌کند. OTP به موبایل همان امضاکننده ارسال می‌شود.

۴. **منبع و محل امضا:** فرانت‌اند فیلدهای اختیاری placement را ارسال نمی‌کند. بک‌اند باید محل پیش‌فرض قابل استفاده روی قرارداد فعلی داشته باشد و سند برگشتی متعلق به همین قرارداد/دور باشد. در صورت نیاز به تنظیم دستی مختصات، قرارداد و رابط مربوط باید جداگانه مشخص شود.

۵. **انقضا و خطای زیرساخت:** ساعت مرورگر صرفاً راهنمای نمایش است. فرانت‌اند برای مجوز به `can_sign` و برای نتیجه به وضعیت امضاکنندگان تکیه می‌کند.

## ۲. قرارداد HTTP مورد استفاده

تمام درخواست‌ها با احراز هویت عادی پروژه و `Accept-Language: fa` ارسال می‌شوند. هیچ شناسهٔ خارجی رخ به مرورگر داده نمی‌شود.

پایه: `/v1/deals/{deal_id}/contract-signature`

- `GET` پایه: snapshot محلی؛ بدون فراخوانی سرویس خارجی.
- `POST /otp`: بدون بدنه؛ snapshot به‌علاوهٔ اطلاعات ارسال پیامک.
- `POST /sign`: بدنهٔ multipart شامل `pin`، `otp` و `signature`.
- `POST /refresh`: بدون بدنه؛ دریافت نتیجه از رخ و اعمال نتیجهٔ قطعی.
- `POST /decline`: بدون بدنه؛ پس از تأیید صریح کاربر.

فرانت‌اند Content-Type آپلود را دستی تعیین نمی‌کند تا مرورگر boundary صحیح multipart را بسازد.

نمونهٔ snapshot مطابق مستند:

```json
{
  "status": "PENDING",
  "expires_at": "2026-11-24T10:00:00Z",
  "completed_at": null,
  "contract_document": "document-uuid",
  "signed_document": null,
  "can_sign": true,
  "signers": [
    {
      "role": "customer",
      "status": "PENDING",
      "signed_at": null,
      "is_you": true
    },
    {
      "role": "beneficiary",
      "status": "PENDING",
      "signed_at": null,
      "is_you": false
    }
  ]
}
```

فیلد `endpoints` مستند نیز می‌تواند بازگردد؛ فرانت‌اند از مسیرهای تعریف‌شدهٔ بالا استفاده می‌کند.

- وضعیت درخواست: `PENDING`, `PROCESSING`, `COMPLETED`, `REFUSED`, `EXPIRED`.
- وضعیت امضاکننده: `PENDING`, `PROCESSING`, `SIGNED`, `FAILED`, `UNKNOWN`, `REFUSED`, `EXPIRED`.
- پاسخ موفق OTP علاوه بر snapshot: `"otp": { "sent": true, "expires_in_seconds": 120 }`.
- پاسخ امضا علاوه بر snapshot: `"signed_signer": "customer"` یا `"beneficiary"`.
- PIN دقیقاً شش رقم؛ OTP رشته است و طول ثابتی در فرانت‌اند فرض نشده است.
- فایل `signature` باید PNG واقعی با MIME برابر `image/png`، هدر PNG و حداکثر ۱٬۰۴۸٬۵۷۶ بایت باشد. کنترل نهایی فایل و decode امن باید در سرور نیز انجام شود.

نمونهٔ ساخت درخواست، بدون مقادیر واقعی حساس:

```js
const body = new FormData()
body.append("pin", pin)
body.append("otp", otp)
body.append("signature", signaturePngFile)
// POST /v1/deals/{deal_id}/contract-signature/sign
```

## ۳. نتایج نامشخص، خطاها و امنیت

- فرانت‌اند در صورت وضعیت `PROCESSING/UNKNOWN` هر امضاکننده، هر ۲۰ ثانیه `/refresh` می‌زند؛ درخواست‌ها هم‌پوشانی ندارند. وضعیت کلی درخواست ممکن است پس از شکست قطعی همچنان `PROCESSING` بماند. در انتظار عادی طرف مقابل، GET محلی انجام می‌شود. در تب مخفی یا دیالوگ بسته polling متوقف است.
- پس از قطع ارتباط یا timeout ارسال امضا، درخواست مجدداً ارسال نمی‌شود؛ ابتدا `/refresh` اجرا می‌شود. تا رفع وضعیت نامشخص و اجازهٔ snapshot جدید فرم مسدود است.
- کنترل idempotency، رقابت درخواست‌ها، reconciliation پس‌زمینه و جلوگیری از امضای تکراری مسئولیت بک‌اند است. بسته‌شدن مرورگر نباید نتیجهٔ عملیات را از بین ببرد.
- handler سراسری پاسخ `400` را به اولین پیام خطا محدود می‌کند، برای نمونه `{"error":"otp.:..."}`. فرانت‌اند خطای فیلدی را از همین قالب می‌خواند و پس از `400` ثبت امضا، پیش از فعال‌کردن دوبارهٔ ارسال، snapshot تازه می‌گیرد تا شکست قطعی را از نتیجهٔ نامشخص تشخیص دهد.
- `FAILED` شکست قطعی و قابل تلاش مجدد است، مشروط به snapshot و `can_sign` تازه. OTP مصرف‌شده نباید دوباره معتبر فرض شود.
- کدهای مورد انتظار: `INVALID_PIN`, `OTP_EXPIRED`, `OTP_USED`, `INSUFFICIENT_BALANCE`, `SIGNATURE_CONFIGURATION`, `UNAVAILABLE_OR_INVALID_RESPONSE`.
- برای فقدان کد ملی معتبر ۱۰رقمی یا موبایل با قالب `09XXXXXXXXX` پیام قابل فهم بازگردد؛ فرانت‌اند لینک `/profile` را ارائه می‌دهد. نحوهٔ صدور/بازیابی PIN در مستند مبنا مشخص نشده و باید توسط تیم محصول/بک‌اند توضیح داده شود.
- `401`: نیاز به احراز هویت مجدد؛ `403`: نداشتن اختیار امضا، بدون خروج از حساب؛ `404`: معامله یا درخواست موجود نیست.
- PIN و OTP نباید در لاگ، telemetry، ذخیره‌سازی، پاسخ خطا یا شناسهٔ idempotency آشکار شوند. فرانت‌اند آن‌ها را فقط موقت در فرم نگه می‌دارد و پس از ارسال پاک می‌کند.

## ۴. قرارداد دریافت سند

`GET /v1/documents/{document_id}/download` با احراز هویت عادی برای `contract_document` و `signed_document` فراخوانی می‌شود.

بک‌اند با `FileResponse` خود فایل را به طرف معامله می‌دهد. فرانت‌اند PDF را پیش‌نمایش می‌کند و برای دانلود نیز همان فایل را ارائه می‌دهد. اگر `signed_document` وجود داشته باشد، همان نسخه جایگزین PDF اولیه در دیالوگ می‌شود؛ بک‌اند نیز امضای بعدی را روی همان نسخه اعمال می‌کند.

سرور باید دسترسی طرفین به هر سند را مستقل کنترل کند. شناسهٔ سند نباید مجوز دسترسی تلقی شود. برای `signed_document` فقط فایل قطعی و معتبر ارائه شود. `contract_document` در دور امضا باید مرجع قابل اتکای سند قابل مشاهده باشد؛ اگر نسخهٔ شامل امضای اول با شناسهٔ متفاوت ارائه می‌شود، snapshot باید شناسهٔ مناسب را منعکس کند.

## ۵. چک‌لیست پذیرش مشترک

- [ ] اکشن `sign` در پاسخ جزئیات برای کاربران مجاز با ساختار فعلی ارائه می‌شود و نام مرحله مبنای فرانت‌اند نیست.
- [ ] طرف اول OTP و PIN صحیح ارسال می‌کند؛ طرف دوم پیش از ثبت قطعی امضای اول مجاز نیست.
- [ ] طرف دوم همان قرارداد دارای امضای اول را امضا می‌کند؛ نتیجهٔ نهایی در جزئیات گردش‌کار و اسناد منعکس می‌شود.
- [ ] ارسال transition عمومی امضا، مجوزهای نامعتبر و دسترسی به سند شخص دیگر رد می‌شوند.
- [ ] قطع ارتباط بعد از ارسال باعث امضای تکراری نمی‌شود؛ refresh و reconciliation نتیجه را برمی‌گردانند.
- [ ] `UNKNOWN`, `PROCESSING`, `FAILED` و خطای OTP با وضعیت و کد قابل تشخیص برمی‌گردند.
- [ ] رد و انقضا باعث جابه‌جایی وجه یا گذار ناخواسته نمی‌شوند.
- [ ] عبور خودکار مرحله، عملیات بانکی معلق و تغییر هم‌زمان معامله در `can_sign` و اکشن‌ها منعکس می‌شوند.
- [ ] اختیار نماینده، دریافت PDF باینری، دسترسی مجدد به وضعیت و نمایش سند نهایی در فهرست اسناد تعیین تکلیف شده‌اند.
- [ ] محدودیت فایل، PIN، OTP، انقضا و محرمانگی داده‌ها در سرور نیز اعمال می‌شود.

تست واقعی نیازمند محیط آزمایشی، دو حساب طرف قرارداد، هویت معتبر و دسترسی آزمایشی به سرویس امضا است. موفقیت build یا پاسخ شبیه‌سازی‌شده، تأیید اتصال واقعی رخ محسوب نمی‌شود.
